обоснование решений

INTEGER для идентификаторов

INTEGER обеспечивает уникальность значений и поддерживает AUTOINCREMENT
Это целочисленный тип который занимает минимум места
Поиск и сравнение целых чисел работают быстрее чем строк
Идентификаторы используются как первичные и внешние ключи
Целочисленный тип для ключей это стандарт в реляционных базах данных

TEXT для дат

В SQLite нет отдельного типа DATE
Дата хранится как строка в формате ISO 8601 то есть YYYY-MM-DD
Такой формат обеспечивает корректную сортировку и сравнение дат
Строки в формате ISO 8601 сравниваются лексикографически и результат совпадает с хронологическим порядком
Например 2025-01-15 меньше 2025-02-20 и это правильно как для строк так и для дат

NUMERIC для цен

Цены это денежные значения где важна точность до копейки
NUMERIC обеспечивает фиксированную точность и не теряет копейки при вычислениях
Если использовать REAL возможны ошибки округления например 0.1 + 0.2 даёт 0.30000000000000004
Для денежных сумм это недопустимо
NUMERIC хранит числа с заданной точностью и подходит для цен

Почему логин должен быть UNIQUE

Логин используется для различения пользователей в системе
Если два пользователя имеют одинаковый логин система не сможет их различить
При авторизации невозможно будет определить кто именно входит
Ограничение UNIQUE гарантирует что каждый логин встречается только один раз
Это защищает от создания дубликатов пользователей

Почему дата заказа имеет DEFAULT

При создании нового заказа дата должна устанавливаться автоматически
Пользователь не должен вводить её вручную
DEFAULT CURRENT_DATE автоматически подставляет текущую дату
Это упрощает вставку данных и исключает ошибки при ручном вводе
Если нужно указать другую дату её можно передать явно при вставке

Почему для заказов использована стратегия RESTRICT а для состава заказов CASCADE

Для заказов выбрана стратегия ON DELETE RESTRICT на поле user_id
Это значит что нельзя удалить пользователя пока у него есть заказы
Заказы это история покупок которую нельзя терять
Удаление пользователя с заказами нарушило бы целостность данных

Для состава заказов выбрана стратегия ON DELETE CASCADE на поле order_id
Это значит что при удалении заказа автоматически удаляются все его позиции
Позиция заказа не имеет смысла без самого заказа
Если заказ удалён его состав тоже должен быть удалён
Это логически правильно и упрощает работу с данными
