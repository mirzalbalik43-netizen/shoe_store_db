# УП.11 №12. Администрирование базы данных SQLite

Проект: «Чудо Обувь», единая база `db/shoe_store.sqlite`.
Тема: роли и права, резервное копирование, восстановление, мониторинг и автоматическое обслуживание.

## 1. Роли и проверка прав

SQLite не имеет встроенного серверного механизма пользователей и ролей. В учебном проекте права проверяются **в Python-приложении** перед выполнением операции. Прямой доступ к файлу SQLite этим словарем не ограничивается, поэтому важны права файловой системы.

В прежней таблице `roles` сохранены исходные роли `Администратор`, `Менеджер`, `Клиент`. Через `src/admin.py` дополнительно зарегистрированы три роли:

| Роль | SELECT | INSERT | UPDATE | DELETE | CREATE | DROP |
| admin_db | Да | Да | Да | Да | Да | Да |
| developer | Да | Да | Да | Нет | Нет | Нет |
| reader | Да | Нет | Нет | Нет | Нет | Нет |



## 2. Резервное копирование

Файл `src/backup_restore.py` содержит две реализации:

1. `backup_simple()` использует `shutil.copy2`. Он подходит для закрытой базы, но при активной записи (особенно в WAL-режиме) может скопировать неполный набор данных.
2. `backup_safe()` использует `sqlite3.Connection.backup()`. Этот способ делает согласованный снимок работающей базы, затем проверяет его через `PRAGMA integrity_check`.


## 3. Проверка целостности и статистика

После включения ролей и безопасности выполнены служебные запросы SQLite:

| Параметр | Значение |
| `PRAGMA integrity_check` | `ok` |
| `PRAGMA page_size` | 4096 байт |
| `PRAGMA page_count` | 32 |
| Размер БД по PRAGMA | 131072 байт |
| Прикладных таблиц | 9 |



## 4. Восстановление после имитации сбоя

Чтобы не разрушать базу из предыдущих практик, сценарий отработан на временном файле, сделанном из `db/shoe_store.sqlite`:

1. Сделан консистентный снимок с `backup_safe()`.
2. В отдельном файле удалены все позиции заказов и три заказа, чтобы имитировать потерю данных.
3. После закрытия соединения выполнена функция `restore(backup_path, db_path=временный_файл)`.
4. Восстановленная база успешно прошла проверку целостности.

| Состояние | Заказов |
| До аварии | 3 |
| После удаления на копии | 0 |
| После восстановления | 3 |


## 5. Автоматизация обслуживания

В файле `src/maintenance.py` реализован сценарий:

1. `check_integrity()` - проверяет физическую целостность базы.
2. `backup_safe()` - создает надежную резервную копию.
3. `get_db_stats()` - выводит размер страницы, количество страниц и таблицы.
4. `clear_old_logs(conn, days=30)` - удаляет записи аудита старше 30 дней с использованием безопасного SQL-параметра `?`.
5. Печатает итоговый отчет.

Очистка старых логов протестирована на RAM-копии с записью за прошедшие 90 дней. Архивировать логи и выбирать срок хранения в настоящей системе следует по политике организации.

## 6. Итог

Роли добавлены без потери старых данных, проверка прав работает, подготовлены две программные резервные копии, восстановление и мониторинг подтверждены реальными тестами. Администрирование выполняется на уровне Python и файловой системы, а не через несуществующие SQL-права SQLite.
